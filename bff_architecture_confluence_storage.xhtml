Архитектура BFF (web-gateway-service): аутентификация, авторизация и межсервисное взаимодействие

Техническая документация · Java Spring · Релиз 4.0.7

1. Общие сведения

В рамках развития backend-архитектуры ЕФР внедряется новый компонент — web-gateway-service, реализующий паттерн Backend for Frontend (BFF) на базе Java Spring.

Основная задача BFF — централизовать обработку запросов frontend-приложения, управление пользовательскими сессиями, аутентификацию и проверку прав доступа. Ранее часть этих процессов выполнялась непосредственно на frontend, а проверка полномочий зависела от связки security-gate, security-adapter-middleware и кастомной административной панели.

В новой архитектуре frontend взаимодействует с Keycloak через BFF, не получая и не сохраняя пользовательские access- и refresh-токены самостоятельно. Управление токенами и серверной сессией переносится на backend, а для хранения состояния сессий используется Redis.

Одновременно меняется подход к управлению доступом. Вместо кастомной административной панели постепенно внедряется штатная ролевая модель Keycloak с использованием групп, ролей и механизмов авторизации ресурсов.

Переход выполняется поэтапно. Часть backend-сервисов продолжает работать по прежней схеме, поэтому новая архитектура предусматривает механизмы совместимости, позволяющие сохранить существующие пользовательские сценарии без повторной аутентификации.

В результате BFF становится единой точкой входа для запросов frontend и основным компонентом, отвечающим за применение политики доступа в новой схеме.

При этом Keycloak продолжает выполнять функции системы идентификации и управления разрешениями. BFF не заменяет Keycloak, а берет на себя взаимодействие с ним и применение полученных решений в рамках обработки запросов.

2. Общая архитектура решения

Новая архитектура строится вокруг web-gateway-service, через который проходят запросы frontend-приложения к backend-сервисам.

Основные компоненты решения:

  • Frontend — клиентское приложение, которое взаимодействует с backend через BFF и использует cookie для поддержания пользовательской сессии.
  • web-gateway-service (BFF) — единая точка входа, отвечающая за аутентификацию, авторизацию, управление сессиями и маршрутизацию запросов.
  • Keycloak — система идентификации, хранения ролевой модели и предоставления разрешений на доступ к защищенным ресурсам.
  • Redis — хранилище серверных сессий BFF, включая пользовательские токены.
  • security-gate — компонент предыдущей архитектуры, который временно сохраняется для обеспечения совместимости с еще не мигрировавшими сервисами.
  • Backend-сервисы — прикладные сервисы ЕФР, к которым BFF обращается посредством проксирования запросов или внутренних интеграционных вызовов.
  • Ingress — инфраструктурный компонент маршрутизации входящих запросов, который также используется в отдельных сценариях взаимодействия с legacy-сервисами.

2.1. Логическая схема компонентов

Frontend → Ingress → web-gateway-service (BFF)
                          ├── Keycloak (аутентификация и разрешения)
                          ├── Redis (Spring Session, токены)
                          └── Backend-сервисы
                               └── security-gate (только переходный период)

Упрощенная логическая схема. Не отражает все сетевые маршруты и протокольные обмены.

В штатном пользовательском сценарии frontend обращается к BFF через ingress. BFF определяет наличие действующей пользовательской сессии, выполняет необходимые проверки доступа и направляет запрос соответствующему backend-сервису.

Взаимодействие с Keycloak и Redis осуществляется на серверной стороне. Frontend не участвует в хранении токенов и не выполняет самостоятельную проверку полномочий.

3. Аутентификация и управление пользовательской сессией

3.1. Изменения в процессе аутентификации

В предыдущей архитектуре frontend самостоятельно инициировал аутентификацию в Keycloak и получал пользовательский токен. Далее токен передавался в security-gate, который сохранял необходимые данные в собственной БД и возвращал клиенту cookie correlation_id.

Полученный идентификатор использовался при последующих обращениях к backend. Проверка прав выполнялась с учетом настроек доступа, заданных через кастомную административную панель.

В новой архитектуре этот процесс переносится в web-gateway-service.

При обращении неаутентифицированного пользователя BFF инициирует процесс аутентификации через Keycloak. После успешного завершения процесса BFF получает пользовательские токены и сохраняет их в серверной сессии.

Для хранения сессий используется Spring Session Redis. Клиенту возвращается cookie SESSION, содержащая идентификатор серверной сессии, а не непосредственно access- или refresh-токен.

3.2. Последовательность аутентификации

  1. Frontend направляет запрос в BFF.
  2. BFF инициирует аутентификацию через Keycloak.
  3. После успешной аутентификации BFF получает токены.
  4. BFF сохраняет состояние пользовательской сессии в Redis.
  5. Клиенту возвращается cookie SESSION.

После создания сессии дальнейшие запросы пользователя обрабатываются с использованием cookie SESSION. BFF извлекает соответствующее состояние из Redis и использует сохраненные данные для выполнения запросов и проверки доступа.

3.3. Хранение сессий в Redis

В новой архитектуре Redis используется как централизованное хранилище серверных сессий.

В рамках Spring Session Redis сохраняются данные пользовательской сессии, включая access- и refresh-токены, полученные при аутентификации.

Такой подход позволяет:

  • исключить необходимость хранения пользовательских токенов на frontend;
  • использовать общее хранилище сессий для нескольких экземпляров BFF;
  • централизовать управление жизненным циклом пользовательских токенов;
  • отделить состояние пользовательской сессии от конкретного экземпляра приложения.

При этом Redis становится критически важной инфраструктурной зависимостью BFF. Недоступность Redis может повлиять на возможность создания, чтения и обновления пользовательских сессий.

3.4. Проверка доступности Redis при запуске

В рамках релиза 4.0.7 доработана библиотека подключения backend-сервисов к Redis. В нее добавлен механизм fail-fast, предназначенный для предотвращения запуска приложения при отсутствии соединения с Redis.

Во время старта приложения выполняется проверка доступности Redis. Если подключение установить не удается, приложение завершает запуск с ошибкой.

Таким образом, экземпляр BFF не должен переходить в рабочее состояние без доступного хранилища сессий.

Механизм fail-fast применяется именно на этапе первоначального запуска приложения. Обработка потери соединения с Redis во время дальнейшей работы сервиса не входит в описанный механизм и должна рассматриваться отдельно.

4. Авторизация и проверка прав доступа

4.1. Централизация проверки прав

Одним из основных изменений новой архитектуры является перенос проверки пользовательских полномочий на уровень BFF.

В предыдущей схеме контроль доступа обеспечивался security-gate и библиотекой security-adapter-middleware, которые использовали настройки, определенные в кастомной административной панели.

В новой схеме BFF отвечает за проверку прав пользователя перед передачей запроса к защищенному backend-ресурсу.

При этом Keycloak используется не только для аутентификации, но и для управления разрешениями на доступ к ресурсам.

4.2. Проверка доступа через UMA

Для проверки пользовательских полномочий используется механизм авторизации Keycloak на основе UMA (User-Managed Access).

Наличие действующей пользовательской сессии и access-токена само по себе не гарантирует доступ к любому защищенному endpoint. При обращении к такому ресурсу BFF дополнительно проверяет наличие соответствующих разрешений через Keycloak.

Общий процесс выглядит следующим образом:

  1. Пользователь обращается к защищенному endpoint через BFF.
  2. BFF определяет пользовательскую сессию и получает необходимые данные аутентификации.
  3. Для запрашиваемого ресурса выполняется проверка прав через механизм UMA в Keycloak.
  4. При наличии разрешения BFF продолжает обработку запроса и направляет его в соответствующий backend-сервис.
  5. Если доступ не разрешен, запрос отклоняется на уровне BFF без обращения к целевому прикладному endpoint.

Таким образом, проверка прав выполняется до передачи запроса нижестоящему сервису.

Реализация сохраняет основной принцип предыдущей архитектуры: пользователь может обратиться только к тем ресурсам, на которые ему предоставлены соответствующие полномочия. При этом управление разрешениями переносится на штатные механизмы Keycloak.

Особенность текущей реализации: проверка доступа к защищенному endpoint предполагает обращение в Keycloak при каждом соответствующем запросе. При текущем количестве активных пользователей такая нагрузка оценивается как приемлемая.

Конкретный технический сценарий UMA, включая используемые запросы и формат получаемых разрешений, требует дополнительного уточнения. В данном разделе зафиксирован подтвержденный принцип работы, без предположений о внутренних деталях протокола.

5. Межсервисное взаимодействие

5.1. Общий подход

В новой архитектуре BFF отвечает не только за обработку пользовательских запросов, но и за взаимодействие с нижестоящими backend-сервисами.

Для межсервисных вызовов используются отдельные механизмы авторизации, которые необходимо отличать от проверки пользовательских прав на входе в BFF.

В текущей реализации предусмотрены два основных сценария:

  • Внутренние интеграционные вызовы, которые BFF инициирует самостоятельно.
  • Проксирование пользовательских запросов к нижестоящим сервисам.

В обоих случаях для взаимодействия с целевыми сервисами предусмотрено использование RPT (Requesting Party Token). При этом получение исходного служебного access-токена осуществляется через механизм Client Credentials.

5.2. Служебная аутентификация BFF

Для выполнения межсервисных запросов используется клиент Keycloak, соответствующий web-gateway-service.

Служебная аутентификация выполняется через OAuth 2.0 Client Credentials. BFF получает access-токен, содержащий роль system, которая используется для идентификации служебного контекста взаимодействия.

Важно разделять два типа токенов:

Тип токена

Назначение

Access token с ролью system

Служебная аутентификация BFF через Client Credentials

RPT

Передача разрешений при взаимодействии с защищенными ресурсами нижестоящих сервисов

Наличие роли system в служебном access-токене не означает, что он автоматически является RPT.

5.3. Использование RPT

При обращении BFF к нижестоящим сервисам используется RPT, предназначенный для авторизованного доступа к защищенным ресурсам.

Для проксируемых запросов дополнительно учитывается audience — идентификатор клиента Keycloak, соответствующего целевому backend-сервису.

Это позволяет формировать контекст авторизации с учетом конкретного сервиса, к которому направляется запрос.

Например, если BFF проксирует запрос к определенному backend-сервису, в процессе получения соответствующего RPT указывается audience этого сервиса.

Такой подход разделяет две задачи:

  • проверку права пользователя обратиться к endpoint BFF;
  • авторизацию последующего обращения BFF к целевому backend-сервису.

Первая выполняется централизованно на BFF через UMA, вторая обеспечивается механизмом межсервисной авторизации с использованием RPT.

Техническая последовательность получения RPT, в том числе конкретный механизм обмена исходного токена, остается предметом дополнительного уточнения.

5.4. Границы ответственности

В новой архитектуре пользовательские проверки доступа централизованы на BFF. Нижестоящие сервисы не выполняют повторную проверку пользовательских полномочий по прежней схеме security-gate.

При этом использование токенов для межсервисного взаимодействия сохраняется как отдельный механизм обеспечения безопасности внутренних вызовов.

Таким образом, BFF принимает решение о допустимости пользовательского запроса, а межсервисная авторизация обеспечивает выполнение разрешенного обращения к соответствующему backend-сервису.

6. Совместимость с предыдущей архитектурой

6.1. Общие принципы перехода

Переход на BFF выполняется постепенно, без одномоментного перевода всех backend-сервисов на новую модель безопасности.

В течение переходного периода в системе одновременно используются две схемы:

  • новая, в которой аутентификация, управление сессиями и проверка пользовательских прав выполняются через BFF;
  • предыдущая, в которой для авторизации и идентификации пользователя используется security-gate.

Для сохранения единого пользовательского сценария реализованы механизмы синхронизации данных между BFF и security-gate.

Основная задача этих механизмов — исключить необходимость повторной аутентификации пользователя при обращении к функциональности, которая еще не переведена на новую архитектуру.

6.2. Поддержка legacy-cookie

После успешной аутентификации пользователя BFF формирует новую серверную сессию и возвращает клиенту cookie SESSION.

Одновременно для обеспечения совместимости с предыдущей архитектурой BFF взаимодействует с security-gate и получает дополнительные cookie:

  • correlation_id — идентификатор, используемый legacy-механизмом для определения пользовательского контекста;
  • efr_user — cookie, сохраняемая для совместимости с существующими пользовательскими сценариями.

Полученные значения передаются клиенту вместе с cookie новой сессии.

В результате в течение переходного периода у пользователя одновременно присутствуют идентификаторы, необходимые для работы обеих архитектур.

При этом основным механизмом управления пользовательской сессией становится SESSION на стороне BFF, а legacy-cookie сохраняются исключительно для обеспечения совместимости.

6.3. Синхронизация пользовательских токенов

В новой архитектуре BFF становится основным владельцем пользовательской сессии и единственным компонентом, ответственным за обновление пользовательских токенов через Keycloak.

После успешной аутентификации данные пользователя, включая access- и refresh-токены, сохраняются в Spring Session Redis.

Дополнительно BFF передает соответствующую информацию в security-gate, где она сохраняется в БД предыдущей архитектуры.

Таким образом, на переходном этапе пользовательские данные поддерживаются одновременно в двух хранилищах:

Хранилище

Назначение

Redis

Основное хранилище сессий и токенов BFF

БД security-gate

Хранение данных для поддержки legacy-механизмов

Источником актуального состояния пользовательских токенов является BFF.

6.4. Обновление токенов

Обновление пользовательских токенов централизовано на стороне BFF.

Если security-gate в процессе обработки запроса обнаруживает истечение срока действия токена, он не выполняет самостоятельное обновление через Keycloak. Вместо этого security-gate обращается к BFF, который отвечает за получение актуальных токенов.

Такое разделение ответственности позволяет избежать ситуации, при которой несколько компонентов независимо используют один и тот же refresh-токен.

Это особенно важно при использовании механизмов ротации refresh-токенов, когда самостоятельное обновление токена несколькими сервисами может приводить к рассинхронизации состояния пользовательской сессии.

В результате в системе сохраняется единый механизм обновления токенов, а security-gate использует его в рамках поддержки предыдущей архитектуры.

7. Особенности маршрутизации и работы Spring Cloud Gateway

7.1. Проксирование запросов

Для реализации gateway-функциональности используется Spring Cloud Gateway Server Web MVC.

BFF выступает промежуточным компонентом между frontend и нижестоящими сервисами, принимая пользовательские HTTP-запросы и перенаправляя их в соответствии с настроенными маршрутами.

Такой подход позволяет централизовать обработку запросов, но требует дополнительного внимания к HTTP-заголовкам, особенно при взаимодействии с сервисами, которые самостоятельно формируют CORS-заголовки.

7.2. Обработка CORS-заголовков

При проксировании запросов через Spring Cloud Gateway может возникать ситуация, когда CORS-заголовки добавляются одновременно нижестоящим сервисом и BFF.

В результате в ответе могут присутствовать дублирующиеся значения, например:

  • Access-Control-Allow-Origin
  • Access-Control-Allow-Credentials

Некорректное сочетание таких заголовков приводит к отклонению ответа браузером из-за нарушения правил CORS.

Для исключения этой проблемы на уровне BFF необходимо явно настроить обработку соответствующих заголовков при проксировании запросов.

В текущей реализации предусмотрено удаление указанных заголовков из проксируемых ответов, чтобы исключить их дублирование при формировании итогового HTTP-ответа.

При этом итоговая CORS-политика должна применяться согласованно на уровне BFF и инфраструктурных компонентов, участвующих в обработке запроса.

7.3. Особенности передачи IP-адреса в legacy-схеме

В переходный период выявлена особенность, связанная с определением IP-адреса пользователя при обращении к сервисам, использующим предыдущую модель безопасности.

В legacy-архитектуре security-gate учитывает IP-адрес источника запроса при проверке пользовательского контекста. Информация об адресе сохраняется в БД и используется при последующих обращениях.

Для определения исходного IP используются прокси-заголовки, в частности X-Forwarded-For и аналогичные механизмы передачи информации об адресе клиента.

Проблема возникает из-за различий в маршрутах прохождения запросов.

При обращении frontend к backend через ingress запрос проходит через инфраструктурный прокси-компонент. В этом случае формируется определенная цепочка прокси-заголовков.

При прямом обращении BFF к backend-сервису через Kubernetes Service или pod запрос проходит по другому маршруту. В результате набор и значения заголовков, используемых для определения IP-адреса, могут отличаться.

Для legacy-механизма это приводит к несоответствию IP-адреса, связанного с пользовательской сессией, и адреса, определяемого при последующем запросе.

7.4. Временное решение

Для обеспечения совместимости вызовы BFF к сервисам, которые продолжают использовать предыдущую схему проверки прав, временно направляются через ingress, а не напрямую по внутреннему маршруту Kubernetes.

Это позволяет сохранить ожидаемую для legacy-механизма схему прохождения запросов и обработки прокси-заголовков.

Данное решение является временным и используется только на период миграции.

После отказа от предыдущего механизма проверки прав необходимость в такой маршрутизации должна быть пересмотрена.

8. Ролевая модель и управление доступом в Keycloak

8.1. Переход на штатные механизмы Keycloak

Одновременно с внедрением BFF выполняется плановый отказ от кастомной административной панели, которая ранее использовалась для управления правами доступа.

В новой архитектуре управление ролями и группами пользователей переносится в Keycloak.

В рамках релиза 4.0.7 в Keycloak созданы группы в соответствии с новой ролевой моделью ЕФР. К группам привязаны соответствующие роли, определяющие полномочия пользователей.

Назначение прав выполняется через включение пользователя в соответствующую группу. При этом пользователь получает роли, назначенные этой группе.

Такой подход позволяет использовать штатные механизмы Keycloak для управления ролевой моделью без необходимости поддерживать отдельную реализацию назначения ролей в кастомной административной панели.

8.2. Разделение realm

Для управления доступом используются два realm Keycloak:

Realm

Назначение

efr

Целевой realm приложения, содержащий бизнес-группы, роли и настройки доступа ЕФР

master

Административный realm, используемый для управления Keycloak и делегирования административных полномочий

Разделение позволяет отделить бизнес-ролевую модель приложения от административных учетных записей, используемых для ее сопровождения.

8.3. Администрирование ролей ЕФР

Для управления пользователями и ролевой моделью в realm master создана отдельная группа «Администратор ролей ЕФР».

Участникам этой группы предоставляются ограниченные административные полномочия для работы с realm efr через стандартный интерфейс Keycloak.

Предусмотрены следующие области управления:

  • пользователи realm efr;
  • группы realm efr;
  • роли realm efr.

Полномочия группы ограничены указанными операциями и не предполагают предоставления полного административного доступа ко всему Keycloak.

Это позволяет передать повседневные операции по управлению пользователями и ролями ответственным сотрудникам без использования кастомной административной панели.

Конкретный механизм ограничения административных полномочий в Keycloak требует отдельного технического подтверждения.

8.4. Синхронизация ролевой модели в переходный период

До завершения миграции в системе одновременно используются новая ролевая модель Keycloak и предыдущая модель, управляемая через кастомную административную панель.

В рамках переходного периода изменения групп и соответствующих назначений необходимо вручную синхронизировать между двумя системами.

Это необходимо для сохранения согласованного поведения сервисов, работающих по разным схемам авторизации.

После полного перевода сервисов на новую архитектуру планируется отказаться от дублирования ролевой модели и использовать Keycloak как единую систему управления ролями и группами.

9. Дополнительные механизмы безопасности

9.1. Завершение пользовательской сессии

В BFF реализован endpoint завершения пользовательской сессии:

[BFF-HOST]/logout

При обращении к нему выполняется завершение серверной сессии пользователя в Redis и удаление связанных с ней cookie на стороне клиента.

В рамках текущей реализации удаляются:

Cookie

Назначение

SESSION

Идентификатор серверной сессии BFF

correlation_id

Идентификатор legacy-сессии security-gate

efr_user

Дополнительная cookie предыдущей архитектуры

Таким образом, после logout пользователь теряет возможность продолжать работу с использованием завершенной сессии BFF.

Отдельный отзыв токенов или завершение SSO-сессии непосредственно в Keycloak в рамках описанного механизма не подтверждены и не рассматриваются как реализованные операции.

9.2. Аутентификация внешних систем

В новой архитектуре дополнительно предусмотрена возможность обращения к защищенным backend-endpoint со стороны внешних систем с использованием HTTP Basic Authentication.

Для этого внешняя система передает учетные данные в HTTP-заголовке Authorization.

Формат заголовка:

Authorization: Basic <base64(username:password)>

В текущей реализации учетная запись для такого взаимодействия создается локально на стороне web-gateway-service.

Этот механизм позволяет организовать доступ внешних интеграций без использования браузерной пользовательской сессии.

Поскольку HTTP Basic Authentication предполагает передачу кодированных, но не зашифрованных учетных данных, такое взаимодействие должно выполняться через защищенное HTTPS-соединение.

Механизм хранения паролей, управления учетными записями и дальнейшего применения авторизации к конкретным ресурсам требует отдельного технического описания.

10. Инфраструктурные зависимости и эксплуатационные особенности

Внедрение BFF изменяет не только схему обработки пользовательских запросов, но и распределение критических зависимостей системы.

Основными компонентами, от которых зависит работа новой схемы, становятся BFF, Keycloak и Redis.

Keycloak

10.1. Особенности отказоустойчивости

Использование Redis позволяет нескольким экземплярам BFF работать с общим состоянием пользовательских сессий. Это упрощает горизонтальное масштабирование приложения, поскольку сессия не привязана к конкретному экземпляру сервиса.

Однако одновременно Redis становится критической точкой зависимости.

При его недоступности BFF может потерять возможность получать или изменять данные пользовательских сессий. Поэтому доступность Redis должна учитываться при проектировании инфраструктуры и мониторинга.

Аналогичным образом необходимо учитывать зависимость BFF от Keycloak, поскольку проверки прав предполагают обращения к системе авторизации при обработке защищенных запросов.

10.2. Особенности производительности

Централизованная авторизация упрощает сопровождение механизмов безопасности, но увеличивает значимость производительности BFF и Keycloak.

При обращении к защищенным endpoint выполняется дополнительная проверка разрешений через Keycloak.

На текущем этапе, с учетом количества активных пользователей, дополнительная нагрузка оценивается как допустимая.

При дальнейшем росте нагрузки потребуется оценивать время выполнения проверок, количество обращений к Keycloak и их влияние на общую задержку обработки пользовательских запросов.

11. Переходный период и целевое состояние архитектуры

Миграция на BFF предусматривает временное сосуществование двух моделей безопасности.

В рамках переходного периода уже реализованы механизмы, обеспечивающие совместимость новой архитектуры с предыдущей. При этом часть решений носит временный характер и должна быть исключена после завершения миграции.

11.2. Целевая архитектура

После завершения миграции предполагается исключить зависимость пользовательских сценариев от security-gate и кастомной административной панели.

В целевой схеме:

  1. Frontend взаимодействует с backend через BFF.
  2. Аутентификация и управление пользовательскими токенами выполняются на стороне BFF с использованием Keycloak.
  3. Пользовательские сессии хранятся в Redis.
  4. Проверка прав доступа к защищенным endpoint централизована на BFF.
  5. Межсервисное взаимодействие выполняется с использованием предусмотренных механизмов токенной авторизации.
  6. Управление группами, ролями и пользователями осуществляется через Keycloak.
  7. Временные механизмы синхронизации с предыдущей архитектурой выводятся из эксплуатации.

При этом отказ от security-gate должен выполняться после завершения миграции зависимых сервисов и подтверждения того, что необходимые пользовательские и интеграционные сценарии работают без legacy-механизмов.

12. Итоги

Внедрение web-gateway-service является одним из основных этапов обновления архитектуры безопасности ЕФР.

Ключевое изменение заключается в переносе управления аутентификацией, пользовательскими сессиями и проверкой прав доступа на серверную сторону. Frontend освобождается от необходимости самостоятельно работать с пользовательскими токенами, а BFF становится единой точкой обработки и авторизации запросов.

Дополнительно новая архитектура позволяет перейти от кастомных механизмов управления доступом к штатным возможностям Keycloak и централизовать управление ролевой моделью.

При этом переход на BFF не является изолированной заменой одного компонента другим. Он затрагивает хранение сессий, межсервисную авторизацию, инфраструктурные зависимости и порядок взаимодействия между backend-сервисами.

Для сохранения работоспособности системы предусмотрен поэтапный переход с поддержкой предыдущей схемы безопасности. После завершения миграции временные механизмы совместимости должны быть выведены из эксплуатации, а Keycloak, Redis и BFF станут основными компонентами новой модели управления пользовательским доступом.
